### Orchestrate

**You own a standing program through durable state.** Use for multi-day work, many PRs, and several independent tracks. One-session work routes to Autonomous run.

## Roles

- **Coordinator.** This chat frames units, writes briefs, drains completions, manages gates, and reports to the user. It does not write product code. It can perform verified branch bookkeeping.
- **Track coordinator.** Optional. Use one only when the root cannot drain that track directly. It owns briefs and rollups for one independent track.
- **Worker or verifier.** An OMP `task` agent with one unit, one branch or worktree, and one report. Use `scout` for read-only research. Use the default task agent for implementation. Give every writer disjoint files and branches.

Keep depth at coordinator, track, worker. Every extra layer needs a complete brief and hides child state from the root.

## Durable store

Set `ORCH_STORE=~/.omp/agent/pstack/orchestrate/<project-slug>`. Run the bundled CLI as:

```bash
bun skill://poteto-mode/scripts/orch/orch.ts --store "$ORCH_STORE" <command>
```

The store contains plain files:

- `preferences.md` or `standing.tsv` contains numbered standing orders. Pass every line into each task brief.
- `overview.md` appends durable project and PR facts.
- `units.tsv` contains unit ID, track, state, branch, PR, SHA, and brief path.
- `frontier.json` contains the current Graphite frontier.
- `ledger.tsv` contains verification verdicts pinned to PR and SHA.
- `inbox/` contains completion pointers.
- `gates.md` contains user decisions with options and a safe default.
- `decisions.tsv` follows **show-me-your-work**.
- `status.md` is generated by `orch status`; do not hand-edit it.

Every file has one writer. Workers publish facts. The coordinator aggregates at drain time.

## Brief contract

Each unit brief is self-contained:

1. Goal and countable done predicate.
2. Exact file, branch, or PR ownership.
3. Inputs and upstream evidence, by repo path or `local://` pointer.
4. Required `skill://` reads, including `skill://poteto-mode` and applicable principles.
5. Real-surface verification command or action.
6. Forbidden paths and side effects.
7. Output contract: commit or report path, SHA, verdict, evidence, and blockers.
8. Instruction to skip project-wide validation; the root runs shared checks after integration.

## Execution

1. **Frame.** Count the units and tracks. State a checkable program predicate. If one agent can finish the work in the active run, use Autonomous run instead.
2. **Initialize.** Run `orch init`. Add standing orders with `orch standing add`. Open the decision trail. Seed existing stack state with `orch frontier set --repo <repo-dir>`.
3. **Pilot one unit.** Take one representative unit through brief, worker, verification, ledger, and integration. Fix the brief and verifier contract from evidence before fan-out.
4. **Scale.** Prepare one worktree per writer. Launch every currently independent unit in one OMP `task` batch. Refill only after a completion changes the ready set. Use fewer broad workers over many tiny workers when ownership remains clear.
5. **Drain.** On each completion, record a pointer with `orch inbox push <agent> <unit> <status> --report <path>`. Finish the current critical write, then run `orch inbox drain`. Classify every pointer, update units with `orch unit add` or `orch unit set`, record verdicts with `orch ledger record`, render `orch status`, and spawn the next ready wave.
6. **Integrate.** Accept only artifacts whose branch, SHA, and evidence match the brief. Reconcile late results against the current frontier. Use a fresh unit to salvage unique work from a stale result; never merge it blind.
7. **Close.** Every unit is terminal, every required verdict is pinned to the current SHA, the frontier matches reality, and `orch status` satisfies the program predicate.

## OMP coordination

- `task` launches asynchronous jobs. Use one batch per ready wave.
- `hub inbox` and `hub jobs` provide live completions and peer messages.
- `hub send` steers a running owner or broadcasts a stop.
- `hub wait` is valid only when no coordinator action remains.
- `hub start` owns long-running watchers, services, and terminal processes that need later input.
- Do not poll task transcripts or resume an agent to ask whether it is alive. Check job state, pushed branches, PRs, and durable store rows.

## Verification ledger

Write one verdict per PR and head SHA with `orch ledger record`. Check it with `orch ledger check` before integration. Valid levels are `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, and `verifier-failed`.

Behavioral work needs a real-surface verdict. CI green is evidence, not a verdict. A worker cannot verify its own behavioral change. A blocked verifier is not a pass. A failed verifier creates a fix unit.

## Stack safety

- Recompute the frontier after every merge, restack, or retarget.
- One root writer owns Graphite topology.
- A verdict is valid only for its recorded SHA. Use patch identity only when it proves no content change.
- Land only the contiguous verified run from the lowest unmerged PR.
- Stop at the first unverified or stale head.

## Failure handling

- Record silent or failed work in the inbox with the last evidence and failure class.
- Capacity failure gets a smaller unit. Network failure gets one same-scope retry. Tool failure gets a valid alternate OMP agent type. Unknown failure gets one retry.
- After two failed retries, abandon the unit and replan around it.
- After an OMP restart, treat prior local tasks as stopped. Re-read standing orders, `units.tsv`, ledger, branches, PRs, and `history://` records. Recompute the frontier and respawn only unfinished units from stored briefs.

## Gates

Park a gate before asking:

```bash
bun skill://poteto-mode/scripts/orch/orch.ts --store "$ORCH_STORE" gate park <id> --question <question> --options <options> --default <answer>
```

Ask only for irreversible actions, genuine product or preference choices, contradictory standing orders, or a program dead end that survived replanning. Route other units around open gates.

**Reply:** predicate and counts from `units.tsv` and `ledger.tsv`, track results, frontier PRs and SHAs, verdict summary, abandoned units, open gates, store path, and decision-trail path.
