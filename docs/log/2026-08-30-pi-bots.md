# Pi Bots

## Problem

Pi had strong one-shot, background, scheduled, and observable subagent execution, but no single roster contract for persistent named teammates that own domains, retain private memory, publish shared owner-written state, and delegate to one another.

## Decision

`plugins/pi-bots/` is a thin Pi extension over `pi-subagents`:

- `~/.pi/agent/BOTS.yml` defines user bots; ancestor `.pi/BOTS.yml` files define project replacements.
- Every enabled domain has exactly one owner. Invalid delegates, ambiguous ownership, unknown fields, and malformed YAML fail closed.
- The effective roster is rendered as an immutable generation and exposed through the atomic `.pi/agents/pi-bots.generated` symlink, using the same effective project-root policy as `pi-subagents`.
- The parent uses the public structured-delegation events for `/bots run`; bot children use the native `subagent` tool for allowed peers.
- Shared domain records are readable across the roster and writable only by the enabled owner through the `bots` tool.
- Private memory follows `memory: project | user | off` independently from the bot definition's config scope.
- Background execution, schedules, status, steering, stop, resume, missions, model fallback, and FleetView remain native `pi-subagents` behavior.

Dynamic runtime-agent registration was tested and rejected as the only discovery mechanism: runtime registrations are process-local, so nested Pi children could not discover peer bots. Registering the same names dynamically and as agent files also caused a native collision. Project-native generated agent files are the smaller, process-safe seam and make scheduled launches discoverable without a second runner.

## Research

Grok Bot established the useful product shape: persistent named teammates, durable memory, shared tools and apps, bot-to-bot collaboration, a chief-of-staff pattern, and recurring routines. Its routine guidance also requires approval for consequential actions, stale/no-data handling, and idempotency.

Hermes Bot Mode established the operational shape: each bot is an isolated profile with persistent memory, skills, credentials, history, cron routines, and peer messaging. Hermes issue 4529 sharpened the state model used here: one file or domain has exactly one writer, while peers can read and route work to the owner.

Pi and `pi-subagents` already supplied execution and lifecycle primitives. Pi Bots therefore adds only roster, ownership, state, prompts, and discovery.

## Implementation

The package contains:

- strict YAML parsing, hierarchical discovery, whole-bot replacement, delegate validation, and unique enabled-domain ownership;
- bounded system prompts with exact runtime identities, charters, peers, delegates, live-state instructions, and native lifecycle guidance;
- immutable generated native-agent rosters with atomic pointer replacement, mandatory `bots` and `subagent` tools, nested delegation, model fallback, thinking, skills, timeout, depth, child extension loading, and writer acceptance;
- foreground structured delegation with exact request correlation, cancellation, and host deadline handling;
- owner-only domain records with `observation`, `inference`, and evidence-required `verified` provenance;
- private memory with explicit project, user, or disabled scope;
- contained no-follow reads and writes, symlink and non-regular-file rejection, crash-recoverable cross-process locks, ownership-transfer preservation, newest-entry rolling limits, strict state frontmatter, safe text normalization, and concurrent first-write handling;
- `/bots` plus the model-callable `bots` tool for list, run, context, record, remember, doctor, and reload.

A starter user roster is installed at `~/.pi/agent/BOTS.yml` with `chief-of-staff`, `engineering`, `research`, and `operations` bots.

Live Pi verification used Pi 0.84.4, `pi-subagents` 0.59.0, and `openai-codex/gpt-5.4-mini` in an isolated project:

1. Parent `bots run` launched `bot.chief-of-staff`.
2. Chief of staff delegated once to `bot.research` with the native child-safe `subagent` tool.
3. Research wrote `FINAL_POINTER_STATE_OK` to its owned `research` domain and `FINAL_POINTER_MEMORY_OK` to project-scoped private memory.
4. Research returned `PEER_POINTER_OK`; chief returned `CHIEF_POINTER_OK` with the peer result.
5. The shared record exists at `~/.pi/agent/team-context/research.md`, matching the user definition scope.
6. The private note exists at the isolated project's `.pi/agent-memory/pi-bots/research/MEMORY.md`, matching `memory: project`.
7. The live generated roster is an atomic symlink to an immutable `.pi/pi-bots-generations/<id>` directory.
8. A leased parent `bots run` let the research child concurrently record `FINAL_SPLIT_LOCK_STATE_OK` and remember `FINAL_SPLIT_LOCK_MEMORY_OK`, proving generation protection does not deadlock nested state writes.
9. Native workflow validation for `bot.operations` returned `{"ok":true,"errors":[]}` for a `runs.run` workflow suitable for `schedule.create`.

## Boundaries

The filesystem ownership policy is an extension contract, not an operating-system sandbox. A bot given direct filesystem mutation tools can bypass the `bots` state API. Generated agent files reserve the `bot.<name>` runtime namespace inside a project. Schedules still require the native `pi-subagents` schedule launcher; Pi Bots does not add a daemon.
